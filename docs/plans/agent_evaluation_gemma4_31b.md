This report gives, for each of the 30 planning questions, gemma4:31b's exact answer, every tool call it made,
and the score against the question's pass criterion. Questions 2 and 30 were asked in two variants, and
question 24 follows question 23 in the same session, so there are 32 prompts. The table was rendered from the
harness report by `scripts/render_agent_evaluation.py`. `agent_question_evaluation.md` explains how to run and

## Method

- **Model and runtime.** gemma4:31b (Q4_K_M) through Hermes Agent 0.21.4 and a loopback Ollama server,
  which loaded it at its full 262,144-token context. Each prompt ran through `AgentController` and
  `HermesAdapter`, the path the Agent tab takes, including the controller's checks and notes. Tools were the 15
  of branch `agent-tool-consolidation` at `c0e500d`.
- **Data.** `/home/alh360/GridLensProjects-eval2`, prepared by `scripts/prepare_agent_evaluation.py`. The
  folder holds a copy of the sample Texas7k project and four runs:
  - A: `2026-07-28_14-46-26`, full branch and generator N-1;
  - B: `2026-09-23_15-42-39`, 603.9 MW of load moved from North Central to Coast;
  - C: `2026-09-24_00-00-00`, run A's results with no analysis;
  - D: `2026-09-24_01-00-00`, failed partway.
- **Procedure.** `scripts/evaluate_agent_questions.py` asked each prompt in a fresh session with the runs it
  names selected, and restored the project after each one. Before question 24, it approved and ran question
  23's saved script in the sandbox image `sha256:f34d86be…`, as the review dialog does. The raw results are in
  `/home/alh360/GridLensProjects-eval2/evaluation_report.json`.
- **Scoring.** Claude scored every answer against its criterion and against the reference facts that
  `scripts/agent_question_references.py` computed, in `/home/alh360/GridLensProjects-eval2/references.json`.
  The references include question 23's interface flow, summed from the index with PyArrow, and the
  violation flags behind question 16's count. The scores are in
  `/home/alh360/GridLensProjects-eval2/scores_gemma4_31b.json`.
- **Verdicts.** Pass means the criterion is met, and every number is right and supported by a call in the
  same turn. Partial means part of the criterion is met, with no wrong fact. Fail means the criterion is not
  met, a fact is wrong, or the cited evidence does not support the claim.
- **nemotron3:33b.** The run began with both models, and was switched to gemma4:31b alone after two
  questions at the user's request. nemotron3:33b's two answers are in the report file, but are not scored
  here.

The 32 prompts took 193 minutes, a median of 176 seconds each. The longest were question 14 (26 minutes),
13 (23), 5 (18), 18 (18), and 23 (17). Gemma made 130 audited tool calls. Four more failed the tool schema and were
rejected before the tool ran: three asked for a field that does not exist, and one qualified cases on
`from_area_name`. No turn ended in a runtime
error.

**What worked.** When gemma chose the call, the tools gave it exact answers:
- the status counts (question 7, which needed the `c0e500d` count fix), margins, contingency rankings,
  per-outage MW, Mvar, and MVA, and the largest change between runs (questions 11, 15, 16, and 19);
- the full sequence of creating a project, configuring it, running GridPACK, and waiting for the run (21);
- a filing draft in which every citation resolves (26);
- the out-of-scope questions (27 and 28);
- building a missing cache before quoting from it (29);
- a nonexistent branch reported as not found (30a).

**What went wrong.**

1. Most of the 16 partial scores omit something the criterion asks for, even when the numbers are right:
   - run statuses (1) and file sizes (2b);
   - `qlim` and `LTC` in both sections (3), and the manifest differences (4);
   - the status filter (5), the match kind (6), and NO_SLACK as zero (7);
   - the rating basis and coverage (9), and persistence against the worst case (10);
   - voltage coverage (17), unmatched facilities (19), the sandbox limits (23), and the untrusted caveat (24).
2. Gemma replaced the project XML without asking (22), although the prompt requires confirmation first.
3. It stated an MVA "remaining capacity" (12), although the prompt says margin is not capacity. The
   controller's note was appended but did not remove the claim.
4. Evidence did not hold up twice. Question 14 cites a query on an area name that does not exist. Question 20
   classified overloads by `overload_count`, which also counts GridPACK violation flags.
5. It answered a file question with no tool call (2a).

**Tool and prompt gaps.** The code was not changed during the run, because the MCP server imports the
worktree's source.

- No tool text says that two `control_area` qualifiers select the ties between two areas. Questions 13,
  14, and 18 took 18 to 26 minutes each, working around it through the cached tables.
- `rank` leaves out objects with no value of the metric. Failed contingencies have no loading, so a `rank` of
  `ISLANDED` contingencies returned none (8).
- `overload_count` counts cases at or above 100% and cases GridPACK flags with `viol`. Flags at 28% to 77%
  loading made question 20's classification wrong. A thermal-only count is needed.
- `read_file` cannot join tables, and the RAW generator section has no area column, so generation by area
  needs a script (5).
- The sandbox mounts the run folder at `/run-data`, but `propose_analysis_script` does not say the results
  are under `/run-data/work` and `/run-data/reports`. Both of gemma's scripts looked at the top level and
  could not run (23, 24).
- `matches` on a bus-number column finds nothing, silently, when given a bus name (12).
- A rule in the prompt did not stop `configure_run` (22). A preview-then-confirm step in the destructive
  tools would.
